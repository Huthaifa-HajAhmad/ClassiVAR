### Phase A: make the case real (DONE 2026-11-04, except the hand check)
- Save and load a case as a JSON file: variant, gene, evidence, records, the gene decision, rules id and version, app version, time stamp (D5, U2, E6).
- The case file holds the rules id and version for the whole case. A per-record version was dropped: for a record from an outside lab the rules used are rarely known.
- A case with an unknown criterion or a strength the rules cannot read is refused with a message that names it. A strength the current rules cap opens, is lowered to today's limit, and the screen says which criteria changed. Opening such a file in a viewer-only mode is not built.
- Done when: a case closed and reopened gives the same class and verdict, and a file saved under older rules says so. The file round trip is covered by tests in `classivar-core`; the Save and Open buttons need one hand check by clicking.

### Phase B: the question that started the project (DONE 2026-11-04)
- Let the curator enter a reported VUS sub-tier ("VUS-low") per record, and show the tier definitions with their sources (C9, E10).
- Show a reason when the tier changes (the engine already supports it). It cannot fire yet: it needs official tier point ranges, which are not published. The verdict says so instead.
- Built: a "Tier it named" row for each record that reported a VUS; the tier shows in the history table, in the verdict (with its definition and source), in a short reference list, and in the saved case file. For a VUS result the screen shows where in the VUS range the points sit, without naming a tier.
- Done when: "how did this variant end up VUS-low?" can be answered on screen. Yes: a lab's tier is recorded and explained, and the evidence behind it is in the history table.

Add each as a note, then as logic, with a source and a worked example:
1. **Done.** PVS1 strength guide (Abou Tayoun 2018): nine situations with short labels, including "does not apply". The chosen situation is saved in the case file and shown on the row. The engine refuses a new PVS1 with no guide answer. Still shortened: it does not walk the tree question by question or apply the gene-level downgrade (Table 1).
2. **Done, needs review.** Strength limits on weak evidence, all recorded as program safeguards. No Supporting-default criterion reaches Very Strong; benign criteria stop at Strong (BP4 at Moderate per Pejaver 2022); BA1 has only stand-alone; PM6 stops at Strong; PM3 now reaches Very Strong per ClinGen 2019. Limits do not apply to earlier records.
3. **Done, with a curator's nuance.** When both sides of the 2015 table are met: if the points also say VUS, the class is VUS (the ordinary conflicting-evidence case); if the points would be confident, the class is withheld with "needs expert judgment" and the criteria on each side are listed. BA1 against evidence that itself reaches Pathogenic is withheld, because known common pathogenic variants exist (the ClinGen exception list).
4. **Done (2026-11-04), needs review.** PP3 and BP4 calibrated thresholds (Pejaver 2022, Table 2) for REVEL, BayesDel without allele frequency, MutPred2 and VEST4, in `[[predictors]]`. A "Predictor score" helper in the criteria list reads a score and offers PP3 or BP4 at the published strength; a score between the limits gives neither. BP4 stays capped at Moderate, so REVEL at or below 0.016 (Strong in the paper) and at or below 0.003 (Very Strong) applies Moderate, and the screen says so. The PM1 + PP3 limit of Strong is a combined cap. Tests use the table's own limits. The numbers were read from the open-access paper (PMC9748256) and cross-checked against my memory of the REVEL row; a reviewer must still check them against the paper. Not built: the other nine tools in the paper, and the paper's advice to choose the tool before seeing its result (the screen only says it).
5. **Done (2026-11-04), needs review.** PS3 and BS3 (Brnich 2019, read from the open-access paper): the citation is in `[[sources]]` and a "Functional assay" helper reads either the number of validation controls (11 or more reaches Moderate, 1 to 10 reaches Supporting, none gives no evidence, and this route goes no higher) or an OddsPath value (above 2.1, 4.3, 18.7 and 350 gives PS3 Supporting, Moderate, Strong and Very Strong; below 0.48, 0.23 and 0.053 gives BS3 Supporting, Moderate and Strong; each limit is crossed strictly; 0.48 to 2.1 gives nothing). The paper's four steps are shown as a reminder only. The paper says even Very Strong functional evidence is not enough alone for Pathogenic; the screen repeats this but the engine does not enforce it. Not built: the assay-class tables, or checking the number of controls against the paper's other conditions.
6. **Done, needs review.** PP1, BS4, PP4 (ClinGen 2024; Am J Hum Genet 111:24-38). **PP1 and PP4 (2026-11-04):** Rule version 0.7.0 adds `[locus_evidence]` (Tables 2, 3 and 4 of the paper, read from the open-access text PMC10806742 in two separate fetches that agreed). A "Family and phenotype" helper turns a diagnostic yield (percent) into PP4 points (Table 2; a yield between two rows takes the lower row) and a count of co-segregating family members into PP1 points (Table 3: 1 point each for dominant and X-linked male, 2 for recessive affected, 0.4 for recessive unaffected). It adds them, cuts the sum to the paper's limit of 5 points, and lists the strength choices Table 4 allows for that total (for example 4 to 4.9 points: PP1 Strong, or PP4 Strong, or PP1 Moderate with PP4 Moderate). The curator picks one; a criterion a choice leaves out is not touched. The points and the total are saved as the reason for each strength. The loader refuses a table whose choice is worth more program points than its band has earned. The existing PP1+PP4 limit of 5 points still withholds the class if the strengths are set by hand above it. Tests cover every row edge of the three tables.
   - **Decision for the reviewer:** the paper's text says PP4 applies only if the yield is "over 20%", but Table 2 starts at 19.1% for 1 point. The table is followed, and the screen says so. Starting at 20 would be the stricter reading.
   - **BS4 done (2026-11-05), needs review.** Rule version 0.8.0 adds `[non_segregation]`. The paper recommends −4 points for non-segregation in autosomal dominant, homozygous recessive and X-linked disease. That is Strong benign here, which was already BS4's default, so no number changed; the paper says it did not formally measure the strength. What it adds is when BS4 does not apply, and a "Non-segregation" helper asks which situation fits: it applies BS4 Strong for "does not follow the disease", and for compound heterozygous recessive cases (little to no evidence), unaffected carriers under reduced penetrance, diseases with many look-alike cases (phenocopy; the paper says valid evidence needs formal segregation analysis), and conflicting results or a very large or complex family (the paper says to use formal linkage analysis) it offers nothing and shows the paper's reason. The wording was read from the open-access paper (Europe PMC copy of PMC10806742) in two fetches; the main page fetch was blocked by a robot check the second time, so a reviewer should compare the situation texts with the paper. Not built: counting individuals for BS4 (the text read gives no per-person table), and how to weigh BS4 against PP1 in one family (the text read does not say).
   - **Corrections after a code review (2026-11-05), checked against the paper:**
     - *Allele sharing.* An earlier screen text said to divide the points by the number of variants. The paper says the opposite: divide the diagnostic yield (a probability) among the variants and read Table 2 again; "one should not divide the points arithmetically". Its example: 95.8% is 7 points; shared by two variants, 47.9% each, which is 2.5 points each. The helper now has a "variants on the same allele" box that divides the yield, with that example as a test. It refuses PP1 when more than one variant shares the allele, because the paper's sharing worksheet (Table S1) was not available.
     - *Who is counted for PP1.* The notes now say which relatives the paper counts: unaffected relatives who do not carry the variant (Table 3 and Figure 3C: the 0.4 points go to an unaffected sibling who "did not inherit the variants"), only if the disease is fully penetrant, never unaffected parents; for dominant disease the text recommends affected relatives only when penetrance is reduced.
     - *Locus homogeneity.* The paper says co-segregation is not evidence, and segregation must not be used to support pathogenicity, when only one gene can cause the phenotype. The helper now asks "Can other genes cause this phenotype?". PP1 is not counted until it is answered, and with "only this gene" only PP4 choices are offered (the highest band with a PP4-only choice, since Table 4 gives maximum strengths).
     - *PP4 cautions from the paper* are shown with the helper (matching phenotype and test, definitive or strong gene-disease validity, caution with high locus heterogeneity, PP4 or PS4 but not both), and a yield below 20% (after sharing) gets a warning.
     - *Engine and loader.* `read_locus` refuses negative and non-numeric points; the saved reason now records the sum before the limit ("sum 6.5 points, counted as 5 (the limit)"); the loader requires the PP1/PP4 combination cap to equal `cap_points`, the standard 1/2/4 point scale, PP1 and PP4 to be pathogenic and BS4 benign, and BS4's strength to be worth 4 points. The saved reasons now cite the rule file's source id and points instead of fixed text.
   - **Not built:** sharing PP1 points among several variants on one allele (needs the paper's Table S1); mixing several family kinds in one calculation (the helper reads one kind at a time, so a family that mixes affected and unaffected recessive carriers needs two readings added by hand); the paper's rules on counting obligate heterozygous females beyond the note; deriving the gene-disease validity requirement for PP4 from the gene link (the helper only shows the caution).
   - **Decisions left for the reviewer:** whether PP4 should start at 20% (as the paper's text says) instead of 19.1% (its table); whether the helper should require the gene link to be established before offering PP4; whether PP1 and BS4 applied together in one family should raise a warning (the text read does not say).

   - **PM6 as a second code for the de novo total (2026-11-07), built, UNVERIFIED.** Rule version 0.12.0 (draft). [ClinGen SVI de novo recommendation v1.1](https://clinicalgenome.org/site/assets/files/3461/svi_proposal_for_de_novo_criteria_v1_1.pdf) (approved 18 March 2018, updated 5 May 2021) was downloaded with curl and read again; Table 1, Table 2 and the extra rules match what `[de_novo]` already held. Table 2 lets either code carry each level (PS2_Supporting or PM6_Supporting, PS2_Moderate or PM6, PS2 or PM6_Strong, PS2_VeryStrong or PM6_VeryStrong), and the paper does not say which to prefer. The "De novo patients" helper now shows two buttons for the same total, "Apply PS2 …" and "Apply PM6 …"; the curator chooses. No number changed. A test covers each level, the recessive lowering, and no points. Applying both PS2 and PM6 now raises a double-counting warning: Table 2 offers either code for one total, not both. Users see it in the notes; no class is withheld.
     - **Decision for the reviewer:** Table 2 lists PM6 at Very Strong, but this program stops PM6 at Strong (a safeguard from Phase C item 2, not a published limit). A total of 4 points offered as PM6 is therefore lowered to Strong, and the screen says "use PS2 for Very strong". Raising the cap would be one line in the rule file; it was left alone because it changes a clinical limit. Parked for later research in "Research backlog" below.
     - **Not built:** a rule for choosing PS2 or PM6 (the paper gives none; the 2015 paper used PS2 for confirmed and PM6 for assumed parentage, which the helper does not enforce), the X-linked and mosaicism rules (notes only).
   - **SpliceAI for PP3/BP4 (2026-11-07), built, UNVERIFIED.** Rule version 0.12.0 (draft) adds SpliceAI to `[[predictors]]` from [Walker 2023](https://pmc.ncbi.nlm.nih.gov/articles/PMC10357475/) (Am J Hum Genet 110:1046-1067), Table 1: a delta score of 0.2 or more gives PP3 and 0.1 or less gives BP4; 0.1 to 0.2 gives nothing. The paper calibrated these limits to Moderate but says to apply the codes at Supporting only, so only Supporting is listed and the paper gives no higher level. The rule file records that calibrated Moderate level (`calibrated`) so the screen can state both, limits the helper to the 0-1 delta range, and asks the curator to confirm the variant is outside donor/acceptor ±1,2 before Apply. It applies outside the donor/acceptor ±1,2 positions only (those use the PVS1 guide); the paper says to remove PP3/BP4 when splicing data later raise a variant to PVS1. The numbers were read from the open-access text in two separate fetches, then checked again against the full page text downloaded with curl (2026-11-07): Table 1 (LR 0.17 for ≤0.1, 1.00 "uninformative" above 0.1 and below 0.2, LR 15.99 for ≥0.2, both rows "moderate"), and the sentence "calibrate codes to reach a moderate level of evidence but only apply predictive PP3/BP4 codes at a supporting weight". Table 1 is for the **maximum** SpliceAI Δ score, which the helper note now says. A third-party page that listed 0.5 and 0.8 tiers is not the paper: the paper mentions 0.5 only as the cutoff of the original SpliceAI paper, says it would leave many spliceogenic variants without a code, and does not adopt it; 0.8 does not appear. Table S6 (the odds thresholds) and Table S11 (splice-region results) are supplements and were not read. A reviewer must compare the numbers with the paper. Each predictor now has a required `reference` field ("Walker 2023, Table 1"), and the saved reason uses it instead of a fixed "Pejaver 2022" text.
   - **Not built from Walker 2023:** using RNA splicing assay results (PVS1 at a chosen strength, BP7, PS3/BS3 for other assays), the other ten tools the paper compared, and the rule that SpliceAI is not combined with a missense tool for the same variant. The helper's line "choose one tool … for the whole case" was written for the missense tools; whether it should apply across SpliceAI and a missense tool is a question for the reviewer.
   - **BA1 reference and PM3 points (2026-11-05), built, UNVERIFIED.** Version 0.10.0 (draft) adds the nine BA1 exception entries from [ClinGen July 2018 Table 1](https://www.clinicalgenome.org/docs/ba1-exception-list/) as a manual reference (transcript variants, ClinVar and Allele Registry ids). No automatic matching or class assignment. Absence is not evidence that BA1 applies; the list is dated, not a live lookup.
   - **PM3:** [ClinGen SVI v1.0, approved 2 May 2019](https://www.clinicalgenome.org/docs/pm3-recommendation-for-in-trans-criterion-pm3-version-1.0/), Tables 1 and 2: confirmed pathogenic/likely pathogenic partner 1 point; unknown phase 0.5 for pathogenic, 0.25 for likely pathogenic; homozygous 0.5 each, capped at 1 total; confirmed uncertain partner 0.25 each, capped at 0.5 total. An uncertain partner with unknown phase earns zero and is not entered. Thresholds 0.5/1/2/4 give Supporting/Moderate/Strong/Very Strong. This corrects the unsupported old claim that no published route reaches Very Strong and raises PM3's cap accordingly. The helper requires confirmation of eligibility and saves counts, capped total, source and confirmation in the reason. Tests cover the published PAH example, every threshold, both row limits, malformed tables, older rules and saved reasons.
   - **Limits for review:** the count-only helper cannot check patient relationships, partner identities, phase, rarity, or independent classification. It asks the curator to check these, including different partner variants for unknown-phase evidence. BA1 entries and PM3 numbers still need a qualified review. No new user decision is needed for this approved scope.

   - **PS2 de novo points (2026-11-05), needs review.** Rule version 0.9.0 (draft) adds `[de_novo]` from the ClinGen SVI "Recommendation for De Novo Criteria (PS2 & PM6)", Version 1.1 (approved 18 March 2018). ## Research backlog

Questions to read up on before changing a rule. Nothing here changes the built-in rule file; each entry says what would change if the answer goes one way.

### PM6 at Very Strong (opened 2026-11-07)

The de novo helper offers one total as PS2 or as PM6. ClinGen SVI v1.1, Table 2 lists `PS2_VeryStrong or PM6_VeryStrong`, but this program caps PM6 at Strong (a Phase C safeguard, not a published limit). A 4-point total applied as PM6 is therefore lowered to Strong, and the screen says "use PS2 for Very strong". Raising the cap is one line in `rules/acmg-amp-points.toml` (`max_strength` on PM6), but it changes a clinical limit, so it waits for a qualified review.

Read before deciding:

- Table 2 and its footnotes in the paper (v1.1, approved 18 March 2018, updated 5 May 2021; <https://clinicalgenome.org/site/assets/files/3461/svi_proposal_for_de_novo_criteria_v1_1.pdf>), especially whether "either code" is a free choice or depends on which parentage rows produced the points.
- The 2015 paper's definition of PM6 ("assumed de novo ... without confirmation of paternity and maternity") and whether Very Strong is consistent with it.
- Later ClinGen guidance and VCEP CSpecs for PM6. The SVI working group was retired in April 2025; check the Variant Classification Guidance page.
- How other public implementations apply PM6 at the top of the scale. Record the source and the date for any table or code copied.
- Whether the Strong cap is still wanted even if the paper allows Very Strong. A safeguard can be stricter than a source, but the difference must stay visible on screen and in the docs.

What would change if the cap is raised: `max_strength` for PM6 in the rule file; the de novo test that expects PM6 at Very Strong to fall to Strong; the PM6 note and the "use PS2 for Very strong" message; the rule version; and this roadmap and `docs/ARCHITECTURE.md`. No engine change is needed: `read_de_novo` already reads PM6 through the same cap as PS2.

Related safeguard (added 2026-11-07): if a curator clicks both "Apply PS2 ..." and "Apply PM6 ..." for one de novo total, the assessment counts both criteria, so the engine now raises a double-counting warning (the same pattern as PVS1 + PP3). No class is withheld; the curator removes one. Keep the warning unless a qualified reviewer decides that two independent observations can justify both codes; Table 2 offers either code for one total.
