The window tests load a real case instead (`view/real_case.rs`): RYR1 NM_000540.3:c.7354C>T (CA024770, ClinVar 65979) with the criteria of its two ClinGen expert-panel classifications (Malignant Hyperthermia Susceptibility VCEP 2023, Likely Pathogenic; Congenital Myopathies VCEP 2026, Pathogenic). A test checks that the loaded rules give each panel's class.
- **Real variants, live.** All 8 live source tests pass, including a new one: the first allele of each of 30 expert panels in the ERepo snapshot is found by its CA id, and the HGVS the registry returns is read by the app's parser and leads back to the same allele. In the real window, the RYR1 variant was checked (identity, both builds, ids), the gene checked against all four sources, 17 lab reports imported from ClinVar (8 without a usable class left out and named), the later panel's criteria applied (Pathogenic, 11 points) and compared with the latest report ("still holds").
- **Clearer results.** The checked variant is one card (MANE name in the code face, gene badge, protein, both builds, ids as chips, who checked and when; `identity_card.rs`, words tested). The gene sources are one card with a row per source and a mark for done, checking or failed, right under the gene box. The editor is grouped into Variant, Gene, Condition and Earlier reports, each with a heading and a hairline. ClinGen conditions are "+" pills (filled with a tick once chosen). Long ClinVar lab names end in "…" and wrap in the rail; long messages wrap.
- **Space.** The window opens maximized (restoring gives 1240 × 900). The rail (236 to 300 px) and the editor sheet (340 to 560 px) grow with the window (tested), and the explanation sections sit two to a row when the stage has room. - **Narrow track.** A block too narrow for "PM2 +1" shows "PM2", then nothing (the hover card still names it), instead of a cut label (tested).
- **Release.** Version 1.0.0; a release profile (thin LTO, stripped); no console window in a release build; an app icon (also embedded in the Windows program file, which GPUI uses for the window and taskbar); `cargo-packager` settings; a Windows installer built locally (`target/packages/classivar_1.0.0_x64-setup.exe`); licence texts of every shipped package (`THIRD-PARTY-LICENSES.html`, cargo-about, permissive licences only); a `release` workflow that builds both installers on a tag and attaches them to a draft release, signing only when certificates are configured; `CHANGELOG.md`; `docs/RELEASE.md` with the checklist.

- **Checked:** the merge gate (app 204, engine 197 + 2 benchmark, sources 42 offline); the live source tests (8); `scripts/gui-smoke.ps1` passes (run with the owner's permission); screenshots of the real case in the maximized window and in both themes.

## Scientific audit and remediation (2026-11-21, rules 0.14.0-draft)

An outside-style scientific audit (`docs/AUDIT-2026-11-21-scientific.md`) found that the variant was unchecked free text, a case had no condition or inheritance mode, a doubtful gene still gave Pathogenic, and several caps, tables and texts were unsourced or incomplete. The owner asked for every finding to be addressed, with Claude as the interim reviewer until a human reviewer (Astra) joins. All findings are addressed below. **The rules stay `unverified`:** an AI review is recorded per entry (`rules/review-signoff.toml`, `docs/review/REVIEW-PACKET.md`) but never makes the file "reviewed"; a test enforces that only human sign-offs on every entry can.

- **Variant identity (C1).** The variant box reads HGVS (`c.`, `n.`, `g.`, `m.` on a versioned transcript or a chromosome accession), positions and VCF rows (`17-43057062-T-TG`; the build is asked, never guessed), SPDI, ClinVar VCV, dbSNP rsID and ClinGen CA ids, including ClinVar's own display form (`NM_007294.4(BRCA1):c.5266dup (p.Gln1756fs)`). A protein change alone, a gene in place of a transcript, an unversioned transcript and an RCV or SCV are refused with what to type instead. The grammar is ported from the Missense-Structural-Explorer project and widened to every variant type (`classivar-core/src/variant/`). **Check variant** asks the ClinGen Allele Registry, which checks the reference base, normalises the variant and returns the CA id, both builds, the MANE Select transcript, the protein change, the ClinVar variation and the rsID. Several alleles (a multi-allelic rsID) wait for the curator's choice; a variant in another gene than the case's is flagged. The identity is saved with the case.
- **Condition and inheritance (C2).** A case names its condition (with a MONDO id when known) and its inheritance. Both can be taken from a ClinGen gene-disease curation of the checked gene, which also suggests the gene answer from its rating. Each earlier record can name its own condition. A record whose MONDO id differs from the case's is shown but never compared; the comparison uses the latest record for the same condition, and with only other-condition records the verdict says so.
- **Gene of uncertain significance (C3).** With the gene-disease link marked doubtful, a Pathogenic or Likely pathogenic result is shown as VUS (Richards 2015, "Evaluating and Reporting Variants in Genes of Uncertain Significance"). The points and pictures still show the evidence, and the comparison names the gene link as the reason. Benign results are left alone (a reading noted for the reviewer).
- **ClinVar import (M4).** "Import labs from ClinVar" reads the variation's germline submissions (NCBI E-utilities, VCV XML): lab, date last evaluated, class, review status and condition become earlier records. Criteria are never invented (ClinVar rarely lists them); codes a lab named in its comment are shown as its words ("The lab's comment names: PS4, PVS1"). A second import skips what is there; at most 30 records, the newest kept.
- **Population frequency helper (M1).** BA1 (Ghosh 2018: above 0.05 in a continental dataset of at least 2,000 alleles; never for a variant on the BA1 exception list, matched by CA id), BS1 (Whiffin 2017: the filtering allele frequency at or above the maximum credible frequency from prevalence, penetrance and contributions; both of the paper's worked examples reproduced) and PM2 (ClinGen 2020, Supporting: absent, or for recessive disease only below a gene-specific limit, as no general number is published). Gene-specific limits replace the general ones.
- **Caps (M2).** Every cap is now the highest level a cited general source supports; a typed reason cannot go above it. PM1, PM4 and PM5 stop at Moderate; PP2, BP1, BP2, BP3 and BP5 at Supporting; BP7 offers only Supporting or Strong (RNA, Walker 2023); PM6 may reach Very Strong (SVI Table 2). Higher levels come from an expert panel's rule file, which **Rules…** opens in a new window (D2 done).
- **PVS1 (M3).** The guide now asks Abou Tayoun 2018 Table 1 first (mechanism established, lower one level, lower two levels, no LoF mechanism). The engine checks that the strength equals the guide's answer lowered by that step; a step below Supporting is no PVS1; a PVS1 saved before 0.14 is set aside on opening with a note, never assumed. The guide text states the NMD rule and the in-frame splicing branch; the whole-gene deletion answer points to the CNV framework.
- **Predictors (M5).** AlphaMissense and VARITY_R from Bergquist 2025 Table 1 (read from the PDF; its REVEL, MutPred2 and VEST4 rows match ours). ESM1b is not added: its scale runs the other way, which the predictor table cannot express yet. SpliceAI with a missense tool: PP3 is one code, apply it once (Walker 2023, Pejaver 2022).
- **Double counting (M6).** PVS1 + PS3 now warns (Brnich 2019, Walker 2023). PS2/PM6 + PP4 and PM1 + PP2 were not added: no source says so.
- **Scope (M7).** The welcome screen and `MVP.md` say what is out of scope (CNV, mitochondrial, somatic, low-penetrance alleles).
- **Smaller items.** The PS1/PM5 citation (m1); functional controls per Brnich (m2: experimental controls required; Supporting with 10 or fewer validation controls, none included; Moderate with 11 or more of both kinds); PS1 and BP7 splicing notes (m3); a note on the evidence behind any applied criterion (m4, "Add a note" under More).
- **New from reading the papers.** BP4 at Moderate had no 2015 row; Pejaver's interim rule is now a marked table row (Likely benign), applied to any Moderate benign evidence.
- **Benchmark (R2).** 13,864 ClinGen expert-panel classifications (ERepo, 2026-11-21) scored from the panels' own criteria: 98.3% of those with evidence reach the panel's class (90.7% by points, 5.5% only via the 2015 table), and none lands on the other side of VUS. A merge-gate test holds these floors (`docs/review/BENCHMARK-erepo.md`). The benchmark changed two rules: PS1 + PM5 is now a caution, not a withheld class (8 panels use both), and BA1 is withheld against pathogenic points that alone reach Likely pathogenic (PVS1 + PM3 at Very Strong then met no 2015 row, and BA1 gave Benign; that pair now meets the "≥2 Very strong" row).
- **Code health.** `view.rs` and `Workbench::new` are within the size limits again (types in `view/types.rs`; fields grouped into `Boxes`, `Handles` and `StageMemory`).
- **Code review follow-ups (2026-11-21).** Save now asks `CaseFile::check` first, so the app never writes a file it would refuse to open (a long ClinVar comment or condition name used to save and then fail on Open). ClinVar imports cut the lab's list of codes after a whole code (ending in "…") and the condition name to the case limit, so the check does not trip on normal imports. The population helper names a frequency or share outside 0 to 1 instead of reading it as an empty box. Accepted on purpose: a gene symbol shaped like an id (`RS1`, `CA2`) is read as the id; the lookup shows what the Registry returned and a gene mismatch is flagged (see `identifier` in `variant/notation.rs`).
- **Checked:** the merge gate passes (195 app, 197 engine, 2 benchmark and 42 offline source tests); the two new live source tests pass against the real services. `scripts/gui-smoke.ps1` passes end to end (2026-11-21). The script's steps were brought up to date with this work: it scrolls to a button before clicking (a row above the visible part of the list ignores a click: the PVS1 row after its guide closes, the functional and co-segregation helper buttons, and Check gene on the example); PM6 is now offered at Very Strong; and the 'raise needs a reason' steps use PM2, as PM1 can no longer go above Moderate. Its capture of PVS1 + PM3 at Very Strong against BS1 + BS2 shows 'Needs expert judgment' and no class.

**Decided 2026-11-21 (AI judgment with sources, audit section 8; a human reviewer may still overturn them):** Moderate benign stays generalised from BP4 to any Moderate benign criterion; benign results in a gene of uncertain significance stay as they are, and the note now names the disease-specific benign criteria to check; Whiffin's ½ stays, and the BS1 finding shows the formula; **two Very Strong criteria now meet a new Pathogenic row** ("Tavtigian 2020 points addition": 16 points; all 58 panel classifications are Pathogenic; PVS1 + PM3_Very Strong against two Strong benign criteria is now withheld instead of shown as Likely pathogenic); the ERepo snapshot stays in the public repository under ClinGen's CC0 1.0 terms, with attribution in `crates/classivar-core/tests/data/README.md`.

**Needs a human reviewer:** every entry marked "not checked" in the sign-off file, and a qualified review of the five decisions above.

The app draws its own title bar with GPUI Kit. An isolated Windows run verified minimize, maximize and restore without using the active desktop. ## Interactive workbench (2026-11-20)

Evidence rows now open the rule, source and recorded reason. A temporary preview scores the current evidence without the selected criterion. Compare reports opens the history and highlights differences for a selected report. The main chart occupies the left pane. Expand explanation hides the editor, and report differences are aligned in three columns. Completed reports can be compared while a draft is unfinished. The overall verdict waits for all reported classes. Next verification is the Windows click-through when the machine is free.

## Evidence track (2026-11-20)

The Evidence view now opens on a class banner (class in large type on its class colour, with the rule version and review status, and the total) and one wide, interactive evidence track that replaces the separate "How the points add up" chart. The track fills the pane at any width. The five class zones are coloured bands, and each counted criterion is a labelled block laid end to end from zero: pathogenic blocks in the upper lane, benign blocks in a lower lane that appears only when both directions have evidence. A marker slides to the new total when evidence changes, and the blocks grow in. Both follow the system's reduced-motion setting. Clicking a block opens its explanation (a card with the direction colour, strength, points, rule summary, reason and source). Clicking it again previews the class without it: the block turns to a dashed outline, a dashed marker shows the preview total, and the card shows "Your evidence → Without X" side by side. Buttons under the track give the same choices from the keyboard. The track is drawn only when a class is shown. Checked by capturing the real window in both themes; the scripted UI smoke test has not been run on this change.

Next, in this order: the same treatment for **Compare reports** (the lab's track drawn above today's, with the changed criteria linked between them); a visual empty state; then the "What it is made of" and "What would change it" sections in the same style.

## CI time (2026-11-21)

Measured on the last run on `main` before this change (run 44751696812, cache cold): macOS 19.5 min and Windows 13.9 min, almost all of it clippy (6.6 and 3.4 min), tests (7.7 and 5.4 min) and build (3.0 and 3.7 min, macOS and Windows) one after another. Dependency debug info is already off in `Cargo.toml`, so that idea was not needed.

- **Separate jobs.** fmt (once, on Linux), clippy, test and build (each on Windows and macOS) and audit now run side by side. A run takes as long as its slowest job instead of the sum of all of them. The checks have new names (`clippy (windows-latest)`, and so on); no branch protection depends on the old `check (...)` names.
- **Cache saved only from `main`.** Pull requests read the cache and never write one, so they cannot fill the repository's 10 GB cache limit (each cache is about 750 MB). A pull request that changes `Cargo.lock` builds its new dependencies without caching them.
- **Prebuilt `cargo-audit`.** Installed with a pinned release of `taiki-e/install-action` (checked against the download's checksum) instead of 3 minutes of compiling. This saves runner time, not wall time, because audit ran in parallel anyway.
- **Measured (run 44883177026, started by hand on the branch, cache cold because the jobs have new names):** the whole run took 10.8 min instead of 19.5. Per job, macOS / Windows: clippy 3.7 / 3.1 min, test 10.2 / 7.7 min, build 10.8 / 7.3 min; fmt 13 s and audit 22 s (it was 3.6 min). The slowest job sets the time: build on macOS.
- **Not measured yet:** a warm-cache run. The first run of the new jobs on `main` is cold; the second is the first warm one. Put its numbers here.
- **Left as it was:** macOS stays on the Intel runner (`macos-15-intel`). An Apple-silicon runner is faster but would test a different CPU than the one chosen on 2026-11-05.

## Section redesign and hover cards (2026-11-20, third round)

No clinical rule, number or behaviour changed. Every class still carries `UNVERIFIED rules vX`, a withheld class still draws no class, and the sections keep the conditions they had.

- **The older sections, redrawn.** Each section of the explanation now has a section head (a small monospaced label over an 18 px title) and sits in a card; space separates them instead of hairlines.
  - **What it is made of** (`makeup.rs`, replaces the lanes): one row per kind of evidence with its criteria as chips, a two-sided bar per kind on one shared length per point, and its net points; the kinds with nothing yet are named on one last row.
  - **What the 2015 table says**: four class cards, each row in the monospaced face with one dot per criterion it asks for, filled where the evidence holds one; a met row gets a check, the word "met" and a light fill.
  - **What would change it** (`what_if.rs`): the class strip with the total, the move up above it and the move down below it as dashed outlined bars on a fluid axis that fills the card (it no longer scrolls sideways).
  - **Records against today** (`timeline.rs`): the same fluid axis under a thin class strip, a bar from zero with a dot at each total, today last and heavier.
  - The fixed-width axis (`axis`, `bar_row`, `SCALE_UNIT`, `POINT_WIDTH`) is gone; every picture now places points with `point_axis::fraction`.
- **Hover card** on dial slices, column blocks and track blocks (`block_tip.rs`): code, strength, signed points and the rule summary, plus what a click does next. The hovered slice gets a faint edge. Click to inspect and click again to preview work as before. On the track the card hangs under the band, opening away from the nearer edge so it stays inside the track (`track::tip_anchor`, tested).
- **Compare reports** uses the same section heads (Verdict, Changes, Timeline, History, Notes, Reference) instead of the older plain headings; the history table sits in a card like the other pictures, and the closing line under the last section is gone. Text-only sections (the changes, the notes, the VUS tiers) stay without a card, as on the Evidence tab.
- **Column layout** (`column/layout.rs`): with earlier reports, the column is up to 340 px wide and used to push the readout out of the stage, cutting the zone names and the total tag off. The readout now sits beside the column only while it keeps 200 px; otherwise it goes above, and a column still wider than the stage scrolls sideways in its own box. The hover card's place is a tested function that keeps it inside the stage, left of the capsule when there is room.
- **Hover card reset**: the card is dropped when the picture, the tab (Evidence or Compare reports) or the mode changes, so it cannot show on a picture it was not opened on.
- **Softer emphasis edges**: the outline around the class shown (dial rim, class strip), the chosen picture on the opening screen and a changed history cell used full-strength ink, which read as a bright white stroke in the dark theme. They now use `look::edge` (the text colour at 0.55); a test keeps it at 3:1 or more on every surface it sits on, in both themes.
- **Track zone names**: each zone gets its full name where it fits in the stage's real width and its short name (B, LB, VUS, LP, P) where it does not (`point_axis::name_fits`, tested), so a narrow stage no longer cuts "Uncertain significance (VUS)" into its neighbour.
- **Size limits.** `dial.rs` and `column.rs` were already over 300 lines before this change; their drawing helpers moved, unchanged, to `dial/paint.rs` and `column/parts.rs`. Functions over 50 lines were split where the redesign had made them long (`workspace`, `helper_section`, `picture_choices`, `verdict_card`). Still over the limit: `Workbench::new` in `view.rs` (62 lines), which is one list of about 50 fields; shortening it means grouping those fields into smaller state types, a change that touches every view file.
- **Checked:** the merge gate passes (174 app, 145 engine, 32 offline source tests); new tests for the grouping by kind, the table's dots, the span on the axis, the hover card's words and its place on the track, when a full zone name fits, and a headless test that moves the simulated pointer over a dial slice, a column block and a track block (dark theme, 960 × 600). Screenshots of the real window in both themes at 1240 × 900 and at a 960-wide window, with the editor open (the narrowest stage) and closed. Posted mouse messages do not count as hover in the real window (GPUI asks Windows where the pointer really is), so the hover card was captured with a temporary build that started with a criterion hovered; that switch is not in the code. `scripts/gui-smoke.ps1` passed on 2026-11-21.
- **Next:** the record chips in a narrow window are still stock buttons; on a narrow track the block labels ("PM2 +1") are cut when a block is only one point wide.

### PM6 at Very Strong (opened 2026-11-07)

The de novo helper offers one total as PS2 or as PM6. ClinGen SVI v1.1, Table 2 lists `PS2_VeryStrong or PM6_VeryStrong`, but this program caps PM6 at Strong (a Phase C safeguard, not a published limit). A 4-point total applied as PM6 is therefore lowered to Strong, and the screen says "use PS2 for Very strong". Raising the cap is one line in `rules/acmg-amp-points.toml` (`max_strength` on PM6), but it changes a clinical limit, so it waits for a qualified review.

Read before deciding:

- Table 2 and its footnotes in the paper (v1.1, approved 18 March 2018, updated 5 May 2021; <https://clinicalgenome.org/site/assets/files/3461/svi_proposal_for_de_novo_criteria_v1_1.pdf>), especially whether "either code" is a free choice or depends on which parentage rows produced the points.
- The 2015 paper's definition of PM6 ("assumed de novo ... without confirmation of paternity and maternity") and whether Very Strong is consistent with it.
- Later ClinGen guidance and VCEP CSpecs for PM6. The SVI working group was retired in April 2025; check the Variant Classification Guidance page.
- How other public implementations apply PM6 at the top of the scale. Record the source and the date for any table or code copied.
- Whether the Strong cap is still wanted even if the paper allows Very Strong. A safeguard can be stricter than a source, but the difference must stay visible on screen and in the docs.

What would change if the cap is raised: `max_strength` for PM6 in the rule file; the de novo test that expects PM6 at Very Strong to fall to Strong; the PM6 note and the "use PS2 for Very strong" message; the rule version; and this roadmap and `docs/ARCHITECTURE.md`. No engine change is needed: `read_de_novo` already reads PM6 through the same cap as PS2.

Related safeguard (added 2026-11-07): if a curator clicks both "Apply PS2 ..." and "Apply PM6 ..." for one de novo total, the assessment counts both criteria, so the engine now raises a double-counting warning (the same pattern as PVS1 + PP3). No class is withheld; the curator removes one. Keep the warning unless a qualified reviewer decides that two independent observations can justify both codes; Table 2 offers either code for one total.
