### Phase A: make the case real (DONE 2026-11-04, except the hand check)
- Save and load a case as a JSON file: variant, gene, evidence, records, the gene decision, rules id and version, app version, time stamp (D5, U2, E6).
- The case file holds the rules id and version for the whole case. A per-record version was dropped: for a record from an outside lab the rules used are rarely known.
- A case with an unknown criterion or a strength the rules cannot read is refused with a message that names it. A strength the current rules cap opens, is lowered to today's limit, and the screen says which criteria changed. Opening such a file in a viewer-only mode is not built.
- Done when: a case closed and reopened gives the same class and verdict, and a file saved under older rules says so. The file round trip is covered by tests in `classivar-core`; the Save and Open buttons need one hand check by clicking.

### Phase B: the question that started the project (DONE 2026-11-04)
- Let the curator enter a reported VUS sub-tier ("VUS-low") per record, and show the tier definitions with their sources (C9, E10).
- Show a reason when the tier changes (the engine already supports it). It cannot fire yet: it needs official tier point ranges, which are not published. The verdict says so instead.
- Built: a "Tier it named" row for each record that reported a VUS; the tier shows in the history table, in the verdict (with its definition and source), in a short reference list, and in the saved case file. For a VUS result the screen shows where in the VUS range the points sit, without naming a tier.
- Done when: "how did this variant end up VUS-low?" can be answered on screen. Yes: a lab's tier is recorded and explained, and the evidence behind it is in the history table.

A "Family and phenotype" helper turns a diagnostic yield (percent) into PP4 points (Table 2; a yield between two rows takes the lower row) and a count of co-segregating family members into PP1 points (Table 3: 1 point each for dominant and X-linked male, 2 for recessive affected, 0.4 for recessive unaffected). It adds them, cuts the sum to the paper's limit of 5 points, and lists the strength choices Table 4 allows for that total (for example 4 to 4.9 points: PP1 Strong, or PP4 Strong, or PP1 Moderate with PP4 Moderate). The curator picks one; a criterion a choice leaves out is not touched. The points and the total are saved as the reason for each strength. The loader refuses a table whose choice is worth more program points than its band has earned. The existing PP1+PP4 limit of 5 points still withholds the class if the strengths are set by hand above it. Tests cover every row edge of the three tables.
   - **Decision for the reviewer:** the paper's text says PP4 applies only if the yield is "over 20%", but Table 2 starts at 19.1% for 1 point. The table is followed, and the screen says so. Starting at 20 would be the stricter reading.
   - **BS4 done (2026-11-05), needs review.** Rule version 0.8.0 adds `[non_segregation]`. The paper recommends −4 points for non-segregation in autosomal dominant, homozygous recessive and X-linked disease. That is Strong benign here, which was already BS4's default, so no number changed; the paper says it did not formally measure the strength. What it adds is when BS4 does not apply, and a "Non-segregation" helper asks which situation fits: it applies BS4 Strong for "does not follow the disease", and for compound heterozygous recessive cases (little to no evidence), unaffected carriers under reduced penetrance, diseases with many look-alike cases (phenocopy; the paper says valid evidence needs formal segregation analysis), and conflicting results or a very large or complex family (the paper says to use formal linkage analysis) it offers nothing and shows the paper's reason. The wording was read from the open-access paper (Europe PMC copy of PMC10806742) in two fetches; the main page fetch was blocked by a robot check the second time, so a reviewer should compare the situation texts with the paper. Not built: counting individuals for BS4 (the text read gives no per-person table), and how to weigh BS4 against PP1 in one family (the text read does not say).
   - **Corrections after a code review (2026-11-05), checked against the paper:**
     - *Allele sharing.* An earlier screen text said to divide the points by the number of variants. The paper says the opposite: divide the diagnostic yield (a probability) among the variants and read Table 2 again; "one should not divide the points arithmetically". Its example: 95.8% is 7 points; shared by two variants, 47.9% each, which is 2.5 points each. The helper now has a "variants on the same allele" box that divides the yield, with that example as a test. It refuses PP1 when more than one variant shares the allele, because the paper's sharing worksheet (Table S1) was not available.
     - *Who is counted for PP1.* The notes now say which relatives the paper counts: unaffected relatives who do not carry the variant (Table 3 and Figure 3C: the 0.4 points go to an unaffected sibling who "did not inherit the variants"), only if the disease is fully penetrant, never unaffected parents; for dominant disease the text recommends affected relatives only when penetrance is reduced.
     - *Locus homogeneity.* The paper says co-segregation is not evidence, and segregation must not be used to support pathogenicity, when only one gene can cause the phenotype. The helper now asks "Can other genes cause this phenotype?". PP1 is not counted until it is answered, and with "only this gene" only PP4 choices are offered (the highest band with a PP4-only choice, since Table 4 gives maximum strengths).
     - *PP4 cautions from the paper* are shown with the helper (matching phenotype and test, definitive or strong gene-disease validity, caution with high locus heterogeneity, PP4 or PS4 but not both), and a yield below 20% (after sharing) gets a warning.
     - *Engine and loader.* `read_locus` refuses negative and non-numeric points; the saved reason now records the sum before the limit ("sum 6.5 points, counted as 5 (the limit)"); the loader requires the PP1/PP4 combination cap to equal `cap_points`, the standard 1/2/4 point scale, PP1 and PP4 to be pathogenic and BS4 benign, and BS4's strength to be worth 4 points. The saved reasons now cite the rule file's source id and points instead of fixed text.

## Research backlog

Questions to read up on before changing a rule. Nothing here changes the built-in rule file; each entry says what would change if the answer goes one way.

### PM6 at Very Strong (opened 2026-11-07)

The de novo helper offers one total as PS2 or as PM6. ClinGen SVI v1.1, Table 2 lists `PS2_VeryStrong or PM6_VeryStrong`, but this program caps PM6 at Strong (a Phase C safeguard, not a published limit). A 4-point total applied as PM6 is therefore lowered to Strong, and the screen says "use PS2 for Very strong". Raising the cap is one line in `rules/acmg-amp-points.toml` (`max_strength` on PM6), but it changes a clinical limit, so it waits for a qualified review.

Read before deciding:

- Table 2 and its footnotes in the paper (v1.1, approved 18 March 2018, updated 5 May 2021; <https://clinicalgenome.org/site/assets/files/3461/svi_proposal_for_de_novo_criteria_v1_1.pdf>), especially whether "either code" is a free choice or depends on which parentage rows produced the points.
- The 2015 paper's definition of PM6 ("assumed de novo ... without confirmation of paternity and maternity") and whether Very Strong is consistent with it.
- Later ClinGen guidance and VCEP CSpecs for PM6. The SVI working group was retired in April 2025; check the Variant Classification Guidance page.
- How other public implementations apply PM6 at the top of the scale. Record the source and the date for any table or code copied.
- Whether the Strong cap is still wanted even if the paper allows Very Strong. A safeguard can be stricter than a source, but the difference must stay visible on screen and in the docs.

What would change if the cap is raised: `max_strength` for PM6 in the rule file; the de novo test that expects PM6 at Very Strong to fall to Strong; the PM6 note and the "use PS2 for Very strong" message; the rule version; and this roadmap and `docs/ARCHITECTURE.md`. No engine change is needed: `read_de_novo` already reads PM6 through the same cap as PS2.

Related safeguard (added 2026-11-07): if a curator clicks both "Apply PS2 ..." and "Apply PM6 ..." for one de novo total, the assessment counts both criteria, so the engine now raises a double-counting warning (the same pattern as PVS1 + PP3). No class is withheld; the curator removes one. Keep the warning unless a qualified reviewer decides that two independent observations can justify both codes; Table 2 offers either code for one total.
