# Architecture and framework

## Framework decision

| Choice | Value | Why |
|---|---|---|
| Language | Rust (1.98 installed, edition 2024) | Strong compile-time checks suit classification logic. |
| UI | **GPUI Kit 0.9** (`gpui-kit` from Longbridge), which re-exports Zed's GPUI | The owner chose GPUI to learn and enjoy it. Kit adds ready-made components (buttons, inputs, dialogs, tabs, charts, themes) so we do not build them. Chosen by the owner on 2026-11-03. |
| Rule data | TOML files | Readable by a reviewer, allows comments, easy to diff. |
| Platforms | Windows now (built and run), macOS next | Team uses both. GPUI Kit supports both; each needs its own build. |

**Risks of this choice.** GPUI Kit and GPUI are young and change quickly. The bundled guides we have describe 0.7, so every API is checked against the 0.9 source when used. Keep `Cargo.lock` in version control and upgrade on purpose, not by accident. The toolchain is pinned in `rust-toolchain.toml`.

## Principles

1. **The rules engine knows nothing about the screen.** It lives in `classivar-core` and is tested alone. A web or command-line front end could reuse it later.
2. **Rules are data.** Changing a rule means editing `rules/*.toml`. Every rule has a `source`, checked at load time.
3. **Validate once, at the edge.** The rule file is checked when loaded. User input is checked when it enters the engine (`AssessError`). Inside, values are trusted.
4. **The curator decides.** The engine never picks criteria.
5. **One owner for each piece of state.** In the UI, the `Workbench` view owns the applied criteria. Parts that only display take values and callbacks.

## How data flows

```
rules/*.toml ──load+check──▶ RuleSet ──┐
                                       ├─▶ RuleSet::assess(&[Applied]) ─▶ Assessment ─▶ screen
curator clicks (Workbench state) ──────┘
```

- `Workbench` holds today's evidence and the records, each a `BTreeMap<code, Choice>` (`Choice` = strength + optional guide-answer id).
- On each draw it builds `Vec<Applied>` and calls `assess` (and, in the reported path, `reevaluate`). The result (points, classes, lanes, conflicts, combined-limit breaches, warnings, next steps) is plain data; the view only draws it. If a result cannot be scored, the screen shows the error instead of stopping.
- `Assessment::class()` is `None` when no criterion is counted, when two criteria contradict each other, when both sides of the 2015 table are met but the points disagree (a confident class would hide the conflict), or when a pair exceeds its combined limit. The screen then shows no class and says which criteria caused it.
- `Assessment.frameworks_agree()` says whether the points and the 2015 table give the same class. A difference is shown as information, not as an error.

## Data sources and how fresh they are

Checked on the web on 2026-11-03. The lookups in `classivar-sources` have live tests (`cargo test -p classivar-sources -- --ignored`) that call the real services; run them before each release and after any report of a wrong answer. A changed address or format is meant to show up as an error, never as "nothing found". Requests identify the program, try again after timeouts, rate limits and server errors (three tries, with waits of 1 and 2 seconds), and cap the size of every answer. The user-agent does **not** carry a contact address yet; EBI-style services expect one, so add it before the team trial.

## Rule content: what was checked against the web

On 2026-11-03 the builder (not a qualified reviewer) compared the rule file with: Richards 2015 Tables 3 to 5 (the combining table matched; several criteria summaries are paraphrases, and PVS1, PS4 and BP1 wording was corrected on 2026-11-04 after the audit); Tavtigian 2020 (1/2/4/8 points; Pathogenic 10 or more, Likely Pathogenic 6 to 9, Likely Benign -1 to -6, Benign -7 or less, via its published summary); the ClinGen PM2 recommendation of 4 September 2020 (PM2 at Supporting; frequency limits differ between gene-specific rule sets); the 2018 ClinGen proposal to stop using PP5 and BP6 (ACMG/AMP made no formal recommendation to remove them). Two status facts were also checked: the ClinGen SVI working group was retired in April 2025 and its recommendations now live on the ClinGen Variant Classification Guidance page; the revised standards (SVCv4.0) were still unpublished, in pilot, when checked.
Added after the audit of 2026-11-04: the ClinGen 2020 combining addition (one Very Strong + one Supporting = Likely pathogenic), withholding the class when contradictory criteria are applied, discouraged criteria listed but not counted in new assessments, and stand-alone benign evidence (BA1) fixed at Benign rather than allowed to be outvoted by points.
Added in the Phase C pass: the PVS1 situation guide from Abou Tayoun 2018 (nine situations, including "does not apply", with the chosen id saved in the case file); PVS1 and PM4 cannot both count; a strength cap on weak evidence (Supporting-default and benign criteria) that does not apply to earlier records; the both-sides rule (a VUS when both methods agree, a withheld class when the points would be confident); and the ClinGen 2024 cap of 5 points on PP1 + PP4. BP4 is now capped at Moderate and PP3 at Strong, per Pejaver 2022. Rule version 0.6.0 (2026-11-04) added the Brnich 2019 functional-evidence limits (`read_functional_controls`, `read_oddspath`); an assay with no validation controls gives no evidence (`controls_supporting_min = 1`); a case file now also carries an optional `reason` for each criterion. Rule version 0.5.0 (2026-11-04) added the calibrated PP3/BP4 score limits for REVEL, BayesDel (no allele frequency), MutPred2 and VEST4 (Pejaver 2022, Table 2, read from the open-access paper) and the Pejaver limit of Strong on PP3 + PM1 together. The engine reads a score with `RuleSet::read_predictor`; a published benign level above Moderate is lowered to the BP4 ceiling and shown as such. The helper writes the tool, score and source into the criterion's `reason`, which is saved with the case. Rule version 0.7.0 (2026-11-04) added the ClinGen 2024 PP1/PP4 points arithmetic (Tables 2 to 4, read twice from the open-access paper): `RuleSet::pp4_points` (which divides the yield, never the points, when variants share an allele), `pp1_points` and `read_locus` (which also lists only PP4 choices when one gene causes the phenotype) give the points, the total cut to 5 and the strength choices; a helper in the criteria list applies one choice to PP1 and/or PP4 with the points (and the sum before the limit) saved as the reason. The helper asks whether other genes can cause the phenotype, and does not count PP1 until that is answered or when only one gene does (the paper's locus homogeneity). The points are fractions, which the engine's whole-number scoring does not hold, so the helper only does the paper's arithmetic and the curator applies a whole-number strength from Table 4. Rule version 0.8.0 (2026-11-05) added the BS4 situations from the same paper: `RuleSet::read_non_segregation` gives BS4 Strong only for the situations where the paper supports it (its −4 points equal BS4's existing default, so no points changed), and a helper shows the paper's reason where it does not. Rule version 0.9.0 (2026-11-05) added the ClinGen SVI de novo recommendation v1.1 for PS2: `RuleSet::read_de_novo` adds points per patient (phenotype fit and confirmed parental relationships, Table 1; the "many genes" row adds at most 1 point), reads the total against Table 2 (0.5, 1, 2 and 4 points for Supporting to Very Strong), and lowers the strength one level for a recessive condition with no second variant. A helper in the criteria list applies the result as PS2 or as PM6 (Table 2 allows either code), with the patients, the points and the source saved as the reason. Rule version 0.12.0 (2026-11-07) adds SpliceAI to the predictor table (Walker 2023, Table 1; the paper's calibrated Moderate evidence is recorded separately from the Supporting code it advises applying), asks the curator to confirm the variant is outside donor/acceptor ±1,2, accepts only the tool's 0–1 range, and lets the de novo total be applied as PM6; PS2 and PM6 counted together now raise a double-counting warning; each predictor now has a required `reference`, which the saved reason uses. Still to add and verify: RNA splicing assays (the rest of Walker 2023) and PVS1's gene-level downgrade (Table 1 of Abou Tayoun 2018). Rule version 0.13.0 (2026-11-08) adds no numbers; the engine's new `HELPER_CODES` check refuses a strength guide on a criterion the app's helpers set, and PP4 and PS4 read off the same family now raises the double-counting warning the rule file's PP1/PP4 cautions already describe (a reviewer decision note stands in `ROADMAP.md`); a rule file that omits `[[vus_tiers]]` now loads.

## Scientific remediation (2026-11-21, rules 0.14.0-draft)

The audit in `docs/AUDIT-2026-11-21-scientific.md` and its log (section 8) describe each change and its source. In short: caps follow published ceilings (`levels` gives exact choices where a ladder has a gap, BP7); PM6 reaches Very Strong; BA1 uses Ghosh 2018; the PVS1 guide states the NMD rule, has the in-frame branch and is preceded by Abou Tayoun's Table 1 (`[[criteria.gene_level]]`, saved as `gene_level`, checked by the engine); functional controls follow Brnich (`AssayValidation`); a `[population]` table drives BA1, BS1 (Whiffin's maximum credible frequency) and PM2; AlphaMissense and VARITY_R join the predictors (Bergquist 2025); a Moderate benign criterion meets a marked Likely benign row (Pejaver 2022); PVS1 + PS3 and PS1 + PM5 are cautions; BA1 is withheld against pathogenic points that reach Likely pathogenic; a doubtful gene-disease link shows a pathogenic class as VUS. ## Rule file format (summary)

`[meta]` (id, version, `status = unverified | reviewed`; `reviewed` also needs `reviewed_by` and `reviewed_on`), `[[sources]]`, `[points]`, `[class_min_points]`, `[[vus_tiers]]` (optional `min_points`), `[[exclusive_pairs]]`, `[[combination_caps]]` (two criteria, `max_points`, reason, source), `[locus_evidence]` (source, `cap_points`, `yield_text_minimum`, `homogeneity_text`, `notes`, a `pp4_yield` table, `segregation` kinds with `points_each`, and Table 4 `bands` whose options name a PP1 and/or PP4 strength; the loader refuses an option worth more program points than its band's lower edge), `[non_segregation]` (source, the BS4 `strength`, and `[[non_segregation.situations]]` each with an id, label, `applies` and text; at least one must apply), `[functional]` (source, `controls_moderate_min`, OddsPath `pathogenic` and `benign` limit lists, crossed strictly), `[[predictors]]` (id, name, source, `reference` — the paper and table as it is written in a saved reason — optional `calibrated` evidence strength when the paper advises applying the code lower, optional `min_score`/`max_score` as a pair, optional `eligibility` text the curator must confirm, optional note, `pathogenic` and `benign` lists of `{ strength, at }` score limits, weakest first; load fails when limits run the wrong way, overlap, cite an unknown source, a range is one-sided or reversed, eligibility is empty, or a limit is stronger than its calibrated strength), `[de_novo]` (source, `recessive_text`, notes, Table 2 `thresholds` as `{ strength, at }`, and `[[de_novo.phenotypes]]` rows with id, label, `confirmed` and `unconfirmed` points, each never lower without confirmed parents, and an optional `max_points`; the helper offers each total as PS2 and as PM6, each read through its own criterion cap), `[pm3]` (source, notes, `thresholds` as `{ strength, at }`, and `[[pm3.rows]]` with id, label, `points` and an optional `max_points`), `[[ba1_exceptions]]` (gene, transcript variant, numeric ClinVar id and unique allele id; a dated manual reference), `[population]` (BA1, BS1 and PM2 sources, `ba1_frequency`, `ba1_min_alleles`, notes), `[[criteria]]` (code, direction, default strength, category, title, summary, source, optional `max_strength`, optional `levels` (exact choices, weakest first), optional `gene_level_source` with `[[criteria.gene_level]]` entries (stable `id`, `short`, `situation`, optional `steps` 0-3; none means the criterion does not apply), `original_strength`, `strength_source`, `discouraged`, `note`, and a `guide_source` with `[[criteria.guide]]` entries: stable `id`, `short` label, `situation` text, and an optional `strength`; no strength means "does not apply").
Loading fails if a criterion or tier cites an unknown source, a code is duplicated, a source id is repeated or empty, a threshold list is out of order or VUS does not start at 0, the points are not strictly increasing or BA1 alone cannot reach Benign, the file has no pathogenic or no benign criteria, a default strength is above its `max_strength` (or a cap cannot be placed), a guide has no source, an empty/duplicate situation or id, no answer at all, or a strength the criterion may not use, **a guide sits on a criterion the app's helpers set (`HELPER_CODES`: PP3, BP4, PS3, BS3, PP1, PP4, BS4, PS2, PM6, PM3 — the helpers cannot answer a guide)**, `original_strength` repeats today's default, an exclusive pair repeats itself or names a missing criterion, a combination cap is below the pair's default total or names a missing criterion, a `reviewed` file has no reviewer or date (and the date must name a possible month and day), `[[vus_tiers]]` is missing entirely (now allowed, defaulting to no tiers) or has empty/repeated tier names, or VUS tier ranges are partial, repeated or outside the VUS range. The newer tables add: a de novo or PM3 table whose source is unknown, whose rows have empty or repeated ids or labels, negative or non-finite points or limits, thresholds that do not rise with the strength or that name a strength the criterion may not use (and de novo rows that give more without confirmed parents, and a recessive text that is empty); and BA1 entries without the `clingen-ba1-2018` source defined, without a gene or variant, with a non-numeric ClinVar id, or with a repeated allele id. The functional and predictor tables additionally require PS3 to be a counted pathogenic criterion, BS3 a counted benign one, PP3 a counted pathogenic one and BP4 a counted benign one. The same checks run when a `RuleSet` is read through serde. A reviewer hash is not implemented yet.

## Supporting several rule-set versions (needed for SVCv4.0)

`RuleSet` is a value, not a global. `RuleSet::builtin()` is only the default (it returns an error instead of panicking, and the program checks it at start-up). The program can also load a file with `--rules`. Every `Assessment` carries the `id` and `version` of the rules that made it (`RuleSetRef`), and a record can carry one too, so a changed rule set can show up as a reason. `CaseFile` writes the case's rule reference and version, and a case saved under other rules says so when it is opened. Per-record rule references are not saved: for a record from an outside lab the rules used are usually unknown. When SVCv4.0 arrives, add a second file and let the user pick.

## Build and run

```
cargo run -p classivar            # run the app
scripts/check.ps1                 # the merge gate (scripts/check.sh on POSIX)
scripts/gui-smoke.ps1             # Windows: drive the real window and save screenshots
cargo run -p classivar -- --rules path/to/file.toml   # try another rule file
```

Full instructions, recipes and debugging: `docs/DEVELOPING.md`.

First build compiles GPUI and takes a few minutes. Windows needs the Visual Studio C++ tools, a Windows SDK and CMake (all present on this machine). macOS has compiled on CI (2026-11-05, `macos-15-intel`) but has never run locally.
Case files are ignored by git (`*.classivar.json`), and the save dialog starts in Documents, so a saved case cannot be committed by accident.
Build output is kept small on purpose: `[profile.dev.package."*"] debug = false` in `Cargo.toml` gives dependencies no debug info and our own crates all of it, measured at 2.1 GB against 5.0 GB for the same workspace (2026-11-06; the 2.1 GB figure also held the test binaries, so the real saving is larger). A backtrace in our code keeps file and line, one inside a dependency keeps only the symbol; `docs/DEVELOPING.md` says how to get the line back. A package rule of that shape beats `CARGO_PROFILE_DEV_DEBUG`, so the variable cannot undo it.
Applied (2026-11-07): `opt-level = 3` for the eight crates the GPUI Kit installation guide lists (`gpui-pre`, `gpui-component`, `gpui-kit`, `gpui-kit-assets`, `gpui-pre-platform`, `rustybuzz`, `taffy`, `ttf-parser`) in `[profile.dev.package]`, so drawing and layout are quick in the dev window. The guide says to leave proc-macro crates such as `gpui-pre-macros` out: they only run inside the compiler, so optimising them adds build time without making the app faster. All eight exist in `Cargo.lock` and Cargo gives no warning. A named-crate rule merges with the wildcard above, so the two do not conflict. The change in how fast the window feels was **not measured** (there is no frame timer yet); the gain in build time or size was not measured either. GPUI Kit also offers an optional `gpui-fast` feature (an alternative GPUI core); it is not enabled and not evaluated.
GPUI Kit 0.9.1 (2026-11-09): the lock is at `gpui-kit` 0.9.1 / `gpui-pre` 0.3.12. The `0.9` requirement in `crates/classivar/Cargo.toml` already allowed the patch, so only `Cargo.lock` changed. It is a backward-compatible release. One API in it mattered: `ColumnFixed::Right` on the kit's own `Table` is the direct answer to the open "pinned Today column" item, but ClassiVAR's history table is drawn by hand (its cells are evidence chips, not delegate rows), so the same split was built directly instead of adopting `Table` — the criterion and Today columns are separate stacks outside the horizontal scroller, with one shared row height so they cannot drift (see `history_table` in `view/panels/history.rs`). The rest of the release's new APIs (`GridLayout`, task checkboxes, `TransitionState`, `Dialog::accessibility_label`, a vertical `Toolbar`, the `WindowBorder` token, right-pinned columns now also in `Table`) belong to components the app does not draw. The input fixes it carries (the platform is told when the caret moves, the first layout happens before an early value is shaped, the caret keeps its visual line at soft wraps) come for free. Its CVE-2026-111943 fix was already in this lock (`rustls-webpki` 0.103.16, `webpki-roots` 1.0.11). `scripts/check.ps1` and `scripts/gui-smoke.ps1` passed, and the screenshots were looked at, on 2026-11-09.

## Known problems and how they were handled

- **Stack overflow on Windows (found 2026-11-04).** Clicking "Reported variant" closed the app with "thread 'main' has overflowed its stack". Windows gives the main thread 1 MB, and the debug build of the old, very large `render` needed more. Two changes: `crates/classivar/build.rs` asks the linker for 16 MB, and the screen is now built from many small functions that each return an `AnyElement`. Tests did not catch it because no test draws the window. `scripts/gui-smoke.ps1` and a real click-through do.
- **A case saved under wider rules (Phase C).** A strength that was legal when a case was saved must still open. Opening validates today's block as recorded, then lowers a capped strength to today's limit and says which criteria changed. A guided criterion with no saved answer gets the matching guide option, so old cases are not rejected.
- **A case or record saved before rules 0.14 with PVS1 (2026-11-21).** Today's PVS1 needs the gene-level answer; it is never assumed, so opening such a case sets PVS1 aside and says so. Earlier records are read as they were made and are not affected.
- **PVS1 is a guide, not a default (Phase C).** A new assessment cannot apply PVS1 without answering which situation fits; the engine rejects it. Earlier records keep the strength the laboratory used, with no guide answer required.


## PM3 and BA1 reference (2026-11-05)

Rule version 0.10.0 adds optional `[pm3]` (source, notes, rows with ids, labels, points and optional row limits, and increasing strength thresholds) and `[[ba1_exceptions]]` (gene, transcript variant, ClinVar id and allele id). Old rule files without them load. The loader checks sources, row ids, finite points and limits, threshold order and strength eligibility, and BA1 identifiers. `RuleSet::read_pm3` sums typed patient counts after each row limit and returns the total and optional strength. PM3's ceiling is now Very Strong, supported by ClinGen 2019 Table 2. Like the rest of the rule file, the PM3 and BA1 content is unverified draft content; `docs/ROADMAP.md` lists the review limits.

The Workbench owns PM3 inputs, eligibility confirmation and panel state, plus BA1 reference visibility. Helpers use existing themed controls. PM3 Apply writes an ordinary criterion with a reason, so saved cases need no new format. Input focus and reset include the new fields. BA1 is a dated manual reference: it does not match the free-text variant or change evidence. The PM3 count-only helper relies on the curator for patient eligibility, partner identity, rarity, phase and independent classification; it cannot verify those facts.

Five engine tests cover the published PAH example, strength edges, both row limits, malformed tables and missing optional data, the nine BA1 identifiers, and PM3 saved-case reopening. The GUI smoke test covers confirmation before Apply, Strong and Very Strong results, both row limits, invalid/empty counts and opening the BA1 list. Live source tests are separate from the merge gate.
