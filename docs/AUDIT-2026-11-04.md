# ClassiVAR — full-stack audit

Date: 2026-11-04. Scope: rules data, core engine, source clients, UI/state, delivery.
Method: four independent reviewers (engine, ACMG content, UI, delivery) plus my own line-by-line read. Every finding below was either read in the code or checked against a primary source; the few unverified items are marked.

**Caveat on "diffs".** `C:\Users\HSA19\ClassiVAR` is not a git repository (`git rev-parse` exits 128). There is no history, so there are no diffs to review. This audit covers the tree as it stands. That absence is itself finding D1.

---

## 1. Verdict

The **arithmetic** is good: the 1/2/4/8 points, the 10/6/0/−6 class thresholds and the 2015 combining table match the published sources row for row.

The **content** is not yet safe to learn from. Two defaults produce wrong answers in common cases (PVS1 start-loss, and the missing PM2 combining rule), and contradictory criteria are still added together.

The **product** is roughly the engine plus one screen. There is no variant identity, no saved case, no lessons, no practice shelf, no ClinVar import. Those are not polish: the teaching half of what was designed does not exist yet.

The **delivery** is a one-day prototype: no version control, no CI, no licence, no macOS build, no application version.

For its current stated use ("research and learning, UNVERIFIED") the engine is usable with supervision. It is not ready for the team trial, and it is not yet the teaching tool the PRD describes.

---

## 2. What is solid

- **2015 Table 5 is implemented correctly**, including the both-sides-met → VUS footnote (`crates/classivar-core/src/assess.rs:171-225`).
- **Points and thresholds match Tavtigian 2020** (1/2/4/8; P ≥ 10, LP 6–9, VUS 0–5, LB −1…−6, B ≤ −7).
- **Upgrade/downgrade arithmetic is correct at every boundary** (verified at 9, 0, −6, −7).
- **Input validation at the engine edge is hard-failing**, not silently ignoring unknown or duplicate criteria (`assess.rs:88-95`).
- **The source layer's failure philosophy is right**: a failure is a distinct state, never an empty answer; a missing ClinGen header is an error; an unknown PanelApp confidence is an error.
- **The async overwrite guard is correct**: `lookup_id` is checked before both success and failure, and lookups run off the UI thread (`crates/classivar/src/view.rs:282-303`).
- **Provenance is visible** on every source card: fetch date, curation date, panel version.
- **Quality gates pass today**: `cargo test --workspace` = 34 passed / 5 ignored, `cargo clippy --workspace --all-targets -- -D warnings` = 0, `cargo fmt --check` = 0, `cargo build --workspace --locked` = 0.

## 5. What this means for the original goal

The original ask was: *teach me ACMG/AMP, walk me through the levels, be interactive and productive, and help me answer "how did this variant get this class, does it still hold, and what would move it".*

What exists answers the **arithmetic** half well: you can see points, class, lanes, and what would change the class. What does not exist is the **explanation** half:

- There is no per-criterion teaching content beyond one sentence and a citation. You cannot practise applying PS2 or PM3 and get feedback.
- There is no practice shelf, so nothing builds the pattern recognition that makes curation fast.
- A reported **VUS-low** cannot even be entered, so the specific question that started the project ("how did it end up VUS-low?") is currently unanswerable in the app.
- Without variant identity or saved cases, it cannot yet be used on a real case and revisited.

So the strategic gap is not more data sources. It is the learning loop and the case record.
